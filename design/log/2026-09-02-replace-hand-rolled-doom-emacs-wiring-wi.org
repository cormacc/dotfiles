** Decisions

- Chose unstraightened over keeping vanilla Doom :: a rarely-used config benefits most from being declarative: zero per-machine bootstrap, updates via flake lock, rollback via HM generations. Rejected:
  - Vanilla Doom tidied: framework stays unmanaged mutable state (the dead comment block documents the failed nix-ification: "doomemacs wants to modify its own directory"); rots between uses; no rollback.
  - Vanilla Doom + =home.activation= clone script: imperative mutation dressed as nix.
- Chose the HM module (=homeModule=, =programs.doom-emacs=) with =provideEmacs = false= :: installs only a =doom-emacs= binary via =home.packages=; verified in module source and by eval that it never touches =programs.emacs=, =~/.config/emacs=, or (with =provideEmacs = false=) =services.emacs.package=. Rejected:
  - Overlay + =pkgs.doomEmacs=: same result, more plumbing; the README's overlay-with-=programs.emacs.package= warning is a hazard we avoid entirely.
- Doom wraps the module-default =pkgs.emacs= (tracking nixpkgs-unstable) :: exactly the combo upstream CI gates and the cachix cache serves. Rejected:
  - Pinned =pkgsEmacs.emacs-pgtk= 30.2: zero cache hits (elisp drvs depend on the wrapping Emacs), extends the 30.2 pin's blast radius; the pin exists for the Spacemacs config, which Doom does not share.
- Hybrid live-edit config :: =init.el=/=packages.el= are canonical in-store (they define the dependency set — a rebuild on change is inherent to any nix-managed Doom); =config.el= is a two-line stub loading =~/dotfiles/editors/emacs/doom/config-live.el= at startup, so day-to-day config edits need no switch. Evidence: dependency scan reads only =init.el= and =packages.el= (upstream =default.nix:110=); the wrapper hard-sets =DOOMDIR= with =--set= so a runtime env override is impossible.
- =inputs.nixpkgs.follows = ""= on the unstraightened input :: upstream-endorsed ("Neither the module nor the overlay uses this input"); this is not the forbidden cache-bypass =follows= pattern from =AGENTS.md= — Doom builds against /our/ =pkgs= regardless.
- Add the upstream cachix cache :: key captured from the cachix API (2026-09-02); registered in both sync-required places per the =lib/nix-caches.nix= header comment.
- =demacs= becomes an alias for the =doom-emacs= binary; the =doom= alias dies :: no doom-sync workflow exists under unstraightened.

** Gotchas

- =doomDir= is =types.pathInStore=: the config must be git-tracked (flake source filter) and the out-of-store symlink pattern used for Spacemacs/Corgi cannot work for it.
- Unstraightened state paths differ from vanilla Doom: profile =nix= puts state under =~/.cache/doom/nix=, =~/.local/share/doom/nix=, etc.; =DOOMLOCALDIR= defaults to =~/.local/share/nix-doom=.
- The unused =doomdir= flake input of unstraightened still gets pinned in =flake.lock= (harmless; we set =doomDir= via the HM option instead).
- *Import-from-derivation makes cross-platform eval impossible.* Because the module =lib.importJSON=s a derivation output, evaluating any configuration that enables =programs.doom-emacs= requires *building* the =doom-intermediates= derivation for that configuration's system. Consequence: the Darwin configuration can no longer be eval-checked from Linux at all — not a slow check, an impossible one. Any future cross-platform "eval-only" acceptance bar in this repository must first check the inputs involved for IFD.
- The =doom-emacs= package installs =bin/doom= and =bin/doomscript=, so deleting the =doom= *alias* did not remove the =doom* command: it changed meaning, from the old clone's =bin/doom= to unstraightened's CLI. =doom sync=/=doom upgrade= are not the workflow under unstraightened.

** Risks

- Doom on tracking Emacs (currently 31.1): mitigated by matching upstream CI's exact combo; if a future =flake update= breaks it, roll back the input pin or set the =emacs= option.
- Darwin: our Darwin nixpkgs is pinned while upstream CI uses unstable, so the Doom elisp set is unverified there until the next Mac build. *Outcome — worse than assessed:* the intended eval-only acceptance turned out to be impossible from Linux (IFD, see =** Gotchas=), so the Mac configuration now carries an entirely unverified Doom until someone builds it there. First Darwin build should be treated as the real test.
- Upstream states its pin translation "will break at times" (build-time only, CI-gated for Doom's own packages); a minimal =packages.el= with no own pins minimises exposure.
- First build is a large one-off elisp build; the cachix cache mitigates. *Outcome:* the build succeeded, but whether the cache actually served it was never measured — a hit depends on our tracking nixpkgs rev being close enough to upstream CI's.

* Implementation

- Coexistence is structural, not incidental. In =home-manager.nix= the module adds =home.packages = [ (if cfg.provideEmacs then cfg.finalEmacsPackage else cfg.finalDoomPackage) ]= and assigns =services.emacs.package= only under =mkIf (options.services ? emacs && cfg.provideEmacs)=. With =provideEmacs = false= the module therefore *cannot* reach =services.emacs=, so Spacemacs's daemon is safe by construction rather than by observation.
- The two-Emacs outcome is deliberate and visible in the built generation: =bin/emacs=, =bin/emacsclient= → =emacs-pgtk-with-packages-30.2= (pinned =nixpkgs-emacs=, for Spacemacs); =bin/doom-emacs= → Doom on =emacs-31.1= (tracking nixpkgs).
- =doomDir= being =types.pathInStore= is what forces the hybrid split; the dependency scan reads only =init.el= and =packages.el=, so =config.el= can be a stub that loads a live file from =~/dotfiles= without affecting the derivation.
- =flake.lock= in the landing commit also carries an unrelated pre-existing refresh of 13 inputs. It was kept rather than reverted because the verified =home-manager switch= was built against exactly this lock; reverting would have committed a state that was never built.
